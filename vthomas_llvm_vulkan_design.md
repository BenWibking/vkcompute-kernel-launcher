# VTHOMAS: Ordinary C++ → Vulkan Compute → RADV/ACO

## Purpose

Build a small THOMAS-like kernel launcher that allows HPC kernels to be written in ordinary C++, compiled to Vulkan compute SPIR-V, and executed through Mesa RADV so that the final AMDGPU machine code is generated by ACO.

The initial target is conventional HPC kernels:

- explicit top-level array/pointer arguments;
- scalar parameters;
- regular indexed array access;
- no pointer chasing;
- no linked data structures;
- no pointers embedded in arbitrary aggregates;
- no requirement for a shader-language frontend.

The compiler path must not use clspv, GLSL, HLSL, Slang, or another source-language translator. Clang remains the only source-language frontend.

The key implementation principle is:

> Keep the C++ kernel body as ordinary LLVM IR. Only lower the kernel boundary to the Vulkan shader ABI.

## LLVM 24 implementation notes

The implemented pass follows this architecture with two LLVM-24-specific
adjustments established by the end-to-end validation tests:

- It emits `llvm.spv.resource.getpointer` for the outer array index (including
  the interior-pointer element offset), then retains ordinary GEPs only for
  nested POD fields. A dynamic outer GEP rooted at `getbasepointer` is rejected
  by LLVM 24's Vulkan logical-pointer access-chain lowering.
- LLVM creates the descriptor `OpVariable` after the IR pass, so the required
  conservative `Aliased` decoration is added by the isolated,
  idempotence-tested `vthomas_spirv_finalize` tool before `spirv-val`.

The compiler pipeline and backend-neutral host ABI are implemented and tested
on macOS. HIP DMA-BUF import, RADV dispatch, and ACO ISA confirmation still
require the Linux AMD runtime backend described below; they cannot be exercised
on the current host.

## High-level architecture

```text
                         ordinary C++ source
                               |
              +----------------+----------------+
              |                                 |
         host clang++                      device clang++
              |                                 |
        Vulkan launcher                       LLVM IR
                                                |
                                  VTHOMAS LLVM ABI pass
                                                |
                                   LLVM SPIR-V backend
                                                |
                                      Vulkan SPIR-V
                                                |
                                           RADV
                                                |
                                       SPIR-V -> NIR
                                                |
                                             ACO
                                                |
                                          AMDGPU ISA
```

The same source can be compiled in separate host and device passes, similar to THOMAS.

The host side provides:

- HIP-pointer-to-Vulkan-buffer import/caching;
- descriptor binding;
- scalar argument packing;
- pipeline creation and caching;
- command submission;
- synchronization.

The device side provides:

- ordinary C++ parsing and optimization through Clang/LLVM;
- a marker identifying kernel functions;
- the `gptr<T>` device pointer type;
- the VTHOMAS LLVM pass;
- final Vulkan SPIR-V generation through upstream LLVM.

## MVP source API

Prefer explicit kernel parameters rather than captured lambdas for the first implementation.

Example:

```cpp
template <class T>
using gptr =
#ifdef VTHOMAS_DEVICE
    T __attribute__((address_space(11))) *;
#else
    T *;
#endif

VTHOMAS_KERNEL
void update(std::size_t i,
            gptr<double> u,
            gptr<const double> flux,
            double dt)
{
    u[i] += dt * flux[i];
}
```

Host launch:

```cpp
double *u;
double *flux;

hipMalloc(&u, n * sizeof(double));
hipMalloc(&flux, n * sizeof(double));

vthomas::parallel_for(n, update, u, flux, dt);
```

For the MVP:

- the first argument is the 1-D invocation index;
- each top-level `gptr<T>` becomes one Vulkan storage-buffer descriptor;
- scalar arguments are packed into push constants;
- a fixed workgroup size such as 256 is acceptable;
- the wrapper performs an `i < n` guard unless the kernel API explicitly takes responsibility for bounds.

Do not initially support lambda capture decomposition or pointer-containing aggregates.

---

## Why descriptor-backed pointers are sufficient

For the intended HPC workload, each pointer is only used as the base of an array.

The compiler ABI can therefore map:

```text
C++ gptr<T>
    |
    v
Vulkan storage-buffer descriptor
    |
    v
spirv.VulkanBuffer
    |
    v
llvm.spv.resource.getbasepointer
    |
    v
ptr addrspace(11)
    |
    v
ordinary LLVM GEP/load/store
```

LLVM already has this resource path.

The relevant upstream implementation/tests are:

- `llvm/docs/SPIRVUsage.md`
- `llvm/test/CodeGen/SPIRV/hlsl-resources/getbasepointer.ll`
- `llvm/test/CodeGen/SPIRV/vk-pushconstant-access.ll`
- `llvm/test/CodeGen/SPIRV/hlsl-intrinsics/SV_DispatchThreadID.ll`

The important upstream IR operations are:

- `llvm.spv.resource.handlefrombinding...`
- `llvm.spv.resource.getbasepointer...`
- `llvm.spv.thread.id.i32`

Upstream LLVM maps Vulkan storage-buffer pointers to address space 11 and push constants to address space 13.

The fact that some of this machinery originated in the HLSL path is not important to VTHOMAS. The pass operates on LLVM IR and can emit the same target extension types and intrinsics directly.

# LLVM pass design

## Pass objective

For every function marked as a VTHOMAS kernel:

1. validate that the signature is supported;
2. leave the original C++ function body essentially unchanged;
3. synthesize a no-argument Vulkan compute entry point;
4. obtain `GlobalInvocationId.x`;
5. reconstruct storage-buffer pointer arguments from Vulkan descriptor bindings;
6. reconstruct scalar arguments from push constants;
7. call or inline the original kernel body;
8. attach the LLVM attributes required for Vulkan compute code generation;
9. ensure the final module is suitable for LLVM's Vulkan SPIR-V backend.

The pass should not attempt general C++ lowering. Clang has already done that.

---

## Kernel discovery

Use a simple source-level marker such as:

```cpp
#define VTHOMAS_KERNEL \
  __attribute__((annotate("vthomas.kernel")))
```

The device compilation should make the annotation discoverable in LLVM IR, for example through `llvm.global.annotations` or an equivalent robust mechanism.

The pass should locate marked functions and build one Vulkan entry point per kernel.

Kernel names should be stable enough that the host runtime can associate:

```text
C++ kernel symbol -> SPIR-V entry point -> VkPipeline
```

For an MVP, an unmangled explicit entry-point name generated from a hash or sanitized symbol name is sufficient.

---

## Kernel signature

MVP-supported form:

```cpp
void kernel(index_type i,
            gptr<T0> a0,
            gptr<T1> a1,
            ...,
            scalar0,
            scalar1,
            ...);
```

Supported pointer arguments:

- top-level `gptr<T>`;
- `const` and non-`const`;
- `T` initially restricted to scalar arithmetic types and simple standard-layout POD element types.

Supported scalars:

- fixed-width integers;
- `size_t`;
- `float`;
- `double`;
- enums represented by supported integer types.

Reject with a clear diagnostic:

- pointer-to-pointer arguments;
- arbitrary generic pointers;
- function pointers;
- references whose ABI is not explicitly supported;
- pointer-containing structs;
- nontrivial C++ objects passed by value;
- virtual objects;
- varargs;
- exceptions crossing the kernel boundary.

---

## Important issue: opaque pointers

LLVM opaque pointers preserve the address space but not the C++ pointee type.

For example:

```llvm
define void @kernel(ptr addrspace(11) %x)
```

does not tell the VTHOMAS pass whether `%x` was originally:

```cpp
float *
```

or:

```cpp
double *
```

However, the Vulkan resource representation must know the buffer element layout. The upstream `spirv.VulkanBuffer` target type carries this information.

Therefore **do not infer pointee types from optimized GEP/load patterns**.

Instead, preserve a small kernel-signature description at device compilation time and consume it in the pass.

### Recommended signature metadata mechanism

The VTHOMAS header should cause Clang to emit companion type information for each kernel argument.

One robust implementation is to emit removable external type-tag globals whose LLVM value types preserve the actual element/scalar type.

Conceptually:

```text
__vthomas_sig_update_arg1 : element type double
__vthomas_sig_update_arg2 : element type double
__vthomas_sig_update_arg3 : scalar type double
```

The pass reads these globals, constructs its internal ABI description, and deletes the metadata globals before final code generation.

The exact representation can change during prototyping, but it must satisfy:

- survives ordinary Clang C++ compilation;
- survives opaque pointers;
- does not depend on debug info;
- does not depend on reverse-engineering optimized instructions;
- can be removed completely after the pass;
- preserves struct element types when simple POD arrays are later supported.

This is likely one of the most important pieces of the MVP.

## Generated entry point

For a source kernel:

```cpp
VTHOMAS_KERNEL
void update(std::size_t i,
            gptr<double> u,
            gptr<const double> flux,
            double dt);
```

the pass should produce IR conceptually equivalent to:

```llvm
define internal spir_func void @update.body(
    i64 %i,
    ptr addrspace(11) %u,
    ptr addrspace(11) %flux,
    double %dt)
{
    ; original C++ body
    ...
}

define void @update.vulkan_entry() #vthomas_compute {
entry:
    %gid32 = call i32 @llvm.spv.thread.id.i32(i32 0)
    %gid   = zext i32 %gid32 to i64

    ; Load n from push constants.
    %n = ...

    %in_range = icmp ult i64 %gid, %n
    br i1 %in_range, label %run, label %done

run:
    ; set=0, binding=0
    %u.handle = call target("spirv.VulkanBuffer", ...)
        @llvm.spv.resource.handlefrombinding...

    %u.base = call ptr addrspace(11)
        @llvm.spv.resource.getbasepointer...(%u.handle)

    ; set=0, binding=1
    %flux.handle = ...
    %flux.base   = ...

    ; scalar push-constant reconstruction
    %dt = ...

    call spir_func void @update.body(
        i64 %gid,
        ptr addrspace(11) %u.base,
        ptr addrspace(11) %flux.base,
        double %dt)

    br label %done

done:
    ret void
}
```

The implementation should copy the exact `spirv.VulkanBuffer`/resource-intrinsic form used by current upstream LLVM tests rather than inventing a parallel representation.

## Compute-shader attributes

LLVM's SPIR-V backend recognizes compute-shader attributes of the form:

```text
"hlsl.shader"="compute"
"hlsl.numthreads"="256,1,1"
```

Despite the names, these are LLVM IR attributes consumed by the backend. The C++ source does not become HLSL.

The VTHOMAS pass should generate the Vulkan entry-point function with these attributes.

For the MVP, use a fixed workgroup size:

```text
256,1,1
```

Later, support a source annotation or runtime-selected specialization.

---

## Global invocation ID

Use the upstream LLVM intrinsic:

```llvm
call i32 @llvm.spv.thread.id.i32(i32 0)
```

LLVM's Vulkan SPIR-V backend lowers this to `GlobalInvocationId.x` and includes the corresponding built-in variable in the `GLCompute` entry point.

Do not synthesize SPIR-V built-in globals manually if the existing intrinsic path works.

# Storage-buffer argument lowering

## One binding per pointer argument

For the MVP:

```text
set 0 binding 0 -> first pointer argument
set 0 binding 1 -> second pointer argument
set 0 binding 2 -> third pointer argument
...
```

This makes the ABI trivial for both compiler and runtime.

Do not initially use:

- descriptor arrays;
- bindless descriptors;
- buffer device addresses;
- PhysicalStorageBuffer pointers.

Those can be future optimizations.

---

## Descriptor-to-pointer lowering

For each `gptr<T>`:

1. construct the appropriate `spirv.VulkanBuffer` target type using the preserved `T`;
2. emit `llvm.spv.resource.handlefrombinding`;
3. emit `llvm.spv.resource.getbasepointer`;
4. obtain `ptr addrspace(11)`;
5. pass this pointer directly to the ordinary C++ kernel body.

Once this pointer exists, ordinary LLVM:

- GEP;
- loads;
- stores;
- arithmetic;
- inlined helper functions

should work normally.

No general transformation of individual memory operations should be necessary.

---

## Interior HIP pointers

The runtime may receive:

```cpp
double *p = base + k;
```

where `base` is the beginning of a HIP allocation.

The Vulkan buffer should normally represent the imported allocation at its base.

Pass the interior offset separately as a scalar ABI field:

```text
descriptor binding -> allocation base
push constant      -> element/byte offset
```

The generated wrapper computes:

```text
actual_pointer = base_pointer + offset
```

before calling the C++ kernel body.

This avoids depending on arbitrary Vulkan descriptor offsets and their alignment restrictions.

The runtime therefore needs to associate every pointer argument with:

```text
allocation base
allocation size
argument byte offset from base
```

The compiler ABI should reserve offset fields for pointer arguments if the host runtime supports interior pointers.

---

# Scalar argument ABI

## MVP approach: packed 32-bit words

Do not initially mirror arbitrary C++ struct layout into Vulkan push constants.

Instead, define a simple deterministic ABI:

```text
push constant payload = array of 32-bit words
```

Examples:

```text
uint32_t -> 1 word
int32_t  -> 1 word
float    -> 1 word
uint64_t -> 2 words
size_t   -> 2 words on the 64-bit target
double   -> 2 words
```

The wrapper reconstructs the original LLVM value.

For example, a `double` can be reconstructed from two `i32` words into an `i64`, then bitcast to `double`.

Advantages:

- trivial host/device agreement;
- no dependence on host C++ padding;
- no `std140`/`std430` ambiguity;
- easy ABI hashing/versioning;
- easy reflection metadata generation.

Use a push-constant block represented with the existing LLVM Vulkan push-constant path, i.e. address space 13.

If the packed payload exceeds the Vulkan push-constant limit, later add a secondary small argument buffer using the same word-packing scheme.

---

# Original kernel body and inlining

The original function should remain ordinary optimized C++ LLVM IR.

The wrapper can initially call it, but before final SPIR-V generation the implementation should inline the kernel body into the Vulkan entry point where practical.

Reasons:

- avoids pointer-valued function arguments in the final shader;
- avoids immediately requiring the full SPIR-V variable-pointer model;
- exposes descriptor-derived pointers and scalar constants to optimization;
- gives LLVM and ACO a cleaner shader entry point.

Recommended pipeline:

```text
Clang frontend
    |
    v
ordinary LLVM optimization
    |
    v
VTHOMAS ABI lowering
    |
    v
inline kernel body into generated entry
    |
    v
cleanup / DCE / simplify
    |
    v
LLVM SPIR-V backend
```

Helper functions used inside the kernel are expected to inline naturally at `-O2`/`-O3`.

For the MVP, diagnose unsupported remaining calls that transport `addrspace(11)` pointers if those produce invalid SPIR-V.

Do not immediately implement general `VariablePointersStorageBuffer` support unless real kernels require it.

---

# Aliasing

This requires an explicit design decision.

HPC kernels may legally receive:

```cpp
kernel(x, x);
```

or overlapping subranges of the same allocation.

Do not assume separate pointer arguments are non-aliasing.

The generated Vulkan/SPIR-V resources should conservatively permit aliasing unless the source argument is explicitly known to be non-aliasing.

The implementation should investigate the exact upstream LLVM representation required to produce the SPIR-V `Aliased` decoration on storage-buffer resources.

Treat this as a Phase-0 validation item.

Longer term:

```cpp
gptr<double> __restrict__ x
```

should be translated into useful non-alias information when possible.

For the MVP, correctness is more important than alias-based optimization.

---

# Pass integration strategy

Implement as an out-of-tree LLVM new-pass-manager plugin.

Development mode:

```text
clang++ -> LLVM bitcode/IR
opt -load-pass-plugin=... -passes=vthomas-lower
llc -mtriple=spirv1.6-vulkan1.3-library -filetype=obj
spirv-val --target-env vulkan1.3
```

Once stable, load the pass directly into Clang with the pass-plugin mechanism.

Do not begin by patching Clang or LLVM upstream.

A stock-LLVM-compatible plugin is the desired baseline.

If an upstream limitation is discovered, isolate it into a small reproducible LLVM test before deciding whether an LLVM patch is necessary.

---

# Device compilation

The exact Clang driver command should be established in Phase 0.

Requirements:

- ordinary C++ language mode;
- SPIR/SPIR-V-compatible target/data layout;
- 64-bit pointers;
- no OpenCL-C or C++-for-OpenCL source mode;
- exceptions disabled;
- RTTI disabled;
- device compilation capable of representing the explicit address spaces used by `gptr<T>`;
- final module retargeted to the Vulkan SPIR-V triple expected by `llc`.

A likely development flow is:

```text
clang++ -std=c++20 ... -emit-llvm
    |
    v
vthomas-lower
    |
    v
llc -mtriple=spirv1.6-vulkan1.3-library
```

Do not lock in the driver flags until a minimal end-to-end prototype has been validated.

# Host runtime contract

The LLVM pass and host runtime must share an ABI description per kernel.

The compiler should emit or separately generate reflection metadata containing:

```text
kernel name
workgroup size
pointer argument count
for each pointer argument:
    descriptor set
    descriptor binding
    element type / ABI type ID
    whether writable/read-only
    offset scalar location
for each scalar argument:
    type
    word offset
    word count
push constant total size
```

The host launcher uses this information to:

- import/cache HIP allocations;
- create/bind VkBuffers;
- update descriptors;
- pack scalar arguments;
- select/create the compute pipeline;
- dispatch the correct number of workgroups.

Avoid making the runtime rediscover the ABI from SPIR-V reflection if the compiler already knows it.

A compact generated C/C++ metadata table or sidecar JSON is sufficient initially.

---

# HIP/Vulkan memory sharing

The runtime should support pre-existing HIP allocations without copying.

Conceptual path:

```text
HIP pointer
    |
    v
hipMemGetAddressRange
    |
    v
allocation base + size + interior offset
    |
    v
ROCr DMA-BUF export
    |
    v
Vulkan external-memory import
    |
    v
VkDeviceMemory
    |
    v
VkBuffer
    |
    v
storage-buffer descriptor
```

Cache the imported representation by HIP allocation base.

Do not import the same allocation on every launch.

The same physical allocation is shared, but the HIP virtual pointer value and Vulkan-visible address do not need to be numerically identical.

For descriptor-backed kernels this does not matter.

Memory import and synchronization are host-runtime work and are outside the LLVM pass.

---

# Synchronization

Synchronization is explicitly outside the compiler pass.

MVP synchronization may be conservative:

```text
HIP work
hipDeviceSynchronize / stream synchronize
Vulkan dispatch
vkQueueWaitIdle / fence
HIP work resumes
```

Later optimize with external semaphores/timeline synchronization.

Do not couple the LLVM pass design to the synchronization mechanism.

# MVP scope

## Required

Support:

- ordinary C++20-ish source accepted by Clang;
- explicitly marked kernel functions;
- one-dimensional `parallel_for`;
- explicit top-level `gptr<T>` arguments;
- top-level arithmetic scalar arguments;
- float/double and fixed-width integer buffer element types;
- `const` buffer arguments;
- descriptor-backed storage buffers;
- push-constant scalar ABI;
- bounds check;
- fixed workgroup size;
- output validated by `spirv-val --target-env vulkan1.3`;
- execution through RADV;
- confirmation that ACO-generated AMDGPU code is produced;
- multiple pointer arguments;
- overlapping/aliased buffers handled correctly;
- interior HIP pointers handled via base + offset.

## Explicitly not required for MVP

Do not implement:

- captured-lambda decomposition;
- arbitrary pointer-containing aggregates;
- pointer chasing;
- linked lists;
- raw buffer-device-address ABI;
- PhysicalStorageBuffer;
- function pointers;
- virtual dispatch;
- device exceptions;
- device RTTI;
- device dynamic allocation;
- recursion;
- arbitrary standard-library runtime support;
- descriptor arrays;
- dynamic workgroup sizes;
- optimized HIP/Vulkan async synchronization.

# Estimated LLVM-pass lift

The compiler pass should be modest if the scope remains explicit-array HPC kernels.

Approximate implementation size:

| Component | Estimated complexity | Approximate LOC |
|---|---:|---:|
| Pass/plugin plumbing | low | 50-100 |
| Kernel discovery | low | 50-100 |
| Signature metadata parsing | medium | 150-300 |
| Signature validation/diagnostics | medium | 100-200 |
| Vulkan entry-point generation | low-medium | 100-150 |
| GlobalInvocationId + bounds | low | 50-100 |
| VulkanBuffer descriptor lowering | medium | 150-250 |
| Push-constant ABI | medium | 150-250 |
| Interior-pointer offset reconstruction | low | 50-100 |
| Aliasing decorations | medium/uncertain | 50-150 |
| Inlining/cleanup integration | low-medium | 50-100 |
| Reflection/ABI metadata output | medium | 100-200 |
| **Core implementation total** |  | **~1,000-1,700 LOC** |

Expect tests to add roughly a similar amount of code.

The largest risks are not the basic wrapper generation. They are:

1. preserving pointee/element types across opaque LLVM pointers;
2. correctly expressing aliasing to SPIR-V/Vulkan;
3. ensuring complicated optimized C++ helper code stays within the subset accepted by LLVM's Vulkan SPIR-V backend;
4. finding any missing LLVM SPIR-V backend features exposed by real HPC kernels.

# Recommended implementation phases

## Phase 0: prove upstream LLVM primitives

Before writing a real pass, manually construct a tiny LLVM IR file that contains:

- one Vulkan compute entry;
- one `spirv.VulkanBuffer` descriptor;
- one `getbasepointer`;
- one `double` load/store;
- one push-constant scalar;
- one `llvm.spv.thread.id.i32` call.

Compile:

```text
.ll -> llc -> .spv -> spirv-val
```

Then execute it on RADV.

Success criterion:

- valid Vulkan 1.3 SPIR-V;
- correct computation;
- RADV accepts pipeline;
- ACO code generation confirmed.

Also validate how to emit `Aliased` on overlapping storage buffers.

This phase should answer all architectural unknowns before significant C++ work.

---

## Phase 1: hand-written C++ kernel + manual ABI metadata

Implement:

```cpp
VTHOMAS_KERNEL
void saxpy(std::size_t i,
           gptr<double> y,
           gptr<const double> x,
           double a);
```

Have the pass recognize it and synthesize the Vulkan wrapper.

Manually describe the signature if necessary.

Success criterion:

```text
ordinary C++ -> LLVM pass -> Vulkan SPIR-V -> RADV/ACO
```

with no clspv or shader-language frontend.

---

## Phase 2: automatic signature metadata

Implement the source/header mechanism that preserves:

- kernel argument categories;
- buffer element types;
- scalar types.

Eliminate manual ABI descriptions.

Add compile-time diagnostics for unsupported signatures.

---

## Phase 3: multiple buffers + HIP import

Add runtime support for:

- multiple descriptors;
- HIP allocation discovery;
- DMA-BUF export/import;
- import cache;
- interior offsets.

Test:

- separate allocations;
- same allocation passed twice;
- overlapping subranges;
- read-only/read-write arguments.

---

## Phase 4: real HPC mini-kernel

Compile a representative production-style kernel containing:

- several arrays;
- structs used as array element types if needed;
- templated helper functions;
- branches;
- math functions;
- substantial inlining;
- `float` and `double`;
- enough control flow to stress LLVM's SPIR-V structurizer.

Compare:

- correctness against HIP;
- generated ACO ISA;
- register count;
- occupancy;
- instruction count;
- runtime.

This phase determines whether LLVM's SPIR-V backend is robust enough for the intended workload.

---

## Phase 5: ergonomics and integration

Add:

- generated reflection metadata;
- CMake integration;
- automatic two-pass compilation;
- embedded SPIR-V blobs;
- pipeline cache;
- better diagnostics;
- optional asynchronous submission.

Only after this should captured lambdas or BDA be considered.

---

# Test plan

## Compiler unit tests

For each pass transformation, use LLVM `FileCheck`-style tests.

Verify:

- kernel discovery;
- binding numbering;
- pointer type preservation;
- push-constant layout;
- scalar reconstruction;
- bounds guard;
- const/read-only handling;
- interior offsets;
- entry-point attributes;
- kernel inlining;
- unsupported-signature diagnostics.

---

## SPIR-V validation tests

Every generated module should pass:

```bash
spirv-val --target-env vulkan1.3 kernel.spv
```

Make this mandatory in CI.

Disassemble selected kernels with:

```bash
spirv-dis
```

and check:

- `OpEntryPoint GLCompute`;
- `GlobalInvocationId`;
- `StorageBuffer`;
- expected descriptor bindings;
- push-constant block;
- alias decorations as required;
- no accidental OpenCL `Kernel` execution model.

---

## Runtime correctness tests

Start with:

1. vector copy;
2. SAXPY;
3. triad;
4. two buffers aliasing exactly;
5. partially overlapping subranges;
6. interior pointer;
7. multiple scalar types;
8. `double`;
9. POD array element;
10. templated helper function;
11. branch-heavy kernel.

Compare byte-for-byte or numerically against HIP implementations.

---

## Backend tests

Confirm execution through:

```text
Vulkan -> RADV -> ACO
```

Capture/disassemble the generated AMDGPU code using Mesa/RADV debugging facilities.

Compare representative kernels with HIP/LLVM-generated AMDGPU ISA.

The goal is not necessarily identical assembly, but:

- semantically correct code;
- reasonable occupancy;
- reasonable VGPR/SGPR usage;
- no obvious Vulkan ABI overhead inside the hot loop;
- descriptors hoisted to base pointers before the main indexed loop/body.

# Key design rules

1. **Clang is the only source-language frontend.**
2. **Do not translate C++ into a shader source language.**
3. **Do not rewrite ordinary array memory operations.**
4. **Lower only the kernel boundary to Vulkan resources.**
5. **Use descriptor-backed StorageBuffer pointers first.**
6. **Preserve pointee types explicitly because LLVM pointers are opaque.**
7. **Use a simple packed scalar ABI.**
8. **Conservatively support aliasing.**
9. **Inline the kernel body into the Vulkan entry point when practical.**
10. **Require `spirv-val` in every compiler test.**
11. **Keep HIP/Vulkan memory import and synchronization outside the LLVM pass.**
12. **Do not expand scope to captured lambdas or pointer-rich objects until real kernels justify it.**

---

# Primary technical risks

## 1. LLVM SPIR-V backend robustness

The main unknown is not descriptor lowering; upstream LLVM already implements that.

The real uncertainty is whether complicated optimized C++ LLVM IR from production HPC kernels consistently survives:

```text
LLVM optimization
    ->
SPIR-V structurization/legalization
    ->
valid Vulkan shader
```

Test representative kernels early.

---

## 2. Pointee-type preservation

Opaque LLVM pointers make this impossible to infer robustly after the fact.

Solve it explicitly with source-generated signature/type metadata.

Do not use debug metadata as a correctness dependency.

---

## 3. Aliasing semantics

Separate Vulkan storage-buffer resources may require explicit aliasing decorations when they overlap.

The MVP must conservatively preserve C++ aliasing behavior.

Validate the exact upstream LLVM mechanism during Phase 0.

---

## 4. Pointer-valued helper calls

If optimized IR retains calls whose parameters are `addrspace(11)` pointers, Vulkan SPIR-V may require variable-pointer capabilities or additional backend handling.

Mitigation:

- compile at `-O2`/`-O3`;
- inline the top-level kernel into the entry point;
- aggressively inline small helpers;
- diagnose unsupported residual cases initially.

# Definition of success

The project is successful when this style of ordinary C++:

```cpp
VTHOMAS_KERNEL
void update(std::size_t i,
            gptr<double> u,
            gptr<const double> flux,
            double dt)
{
    u[i] += dt * flux[i];
}
```

can be launched as:

```cpp
vthomas::parallel_for(n, update, u, flux, dt);
```

where `u` and `flux` are existing HIP allocations, and the implementation:

1. compiles the source with ordinary Clang C++;
2. transforms only the LLVM kernel ABI;
3. emits valid Vulkan compute SPIR-V using upstream LLVM;
4. imports the existing HIP allocations into Vulkan without copying;
5. binds them as storage-buffer descriptors;
6. dispatches through RADV;
7. produces AMDGPU machine code through ACO;
8. matches the HIP implementation numerically;
9. incurs no per-element abstraction overhead from the descriptor ABI.

The preferred MVP is deliberately narrow: explicit arrays plus scalars. Within that scope, the LLVM pass should be an ABI-lowering project rather than a new compiler frontend.
